# 06 RabbitMQ：AMQP 模型与可靠投递

## AMQP 模型与四种 Exchange

### 是什么
RabbitMQ 是 **AMQP 0-9-1** 协议的实现，消息走的是「生产者 → Exchange → Binding → Queue → 消费者」这条链：

- `Connection` 是 TCP 长连接，`Channel` 是连接内复用的轻量逻辑通道（避免每条消息建连接）；`vhost` 做租户级隔离。
- **Exchange 不存消息**，只按类型 + `routing key` + `Binding` 决定把消息投递到哪些队列；消息最终只存在 Queue 里。
- 一条消息可以被路由进**多个队列**（每个队列各拿到一份拷贝），但同一个队列里的一条消息只会被**一个消费者**消费（竞争消费者模式）。

四种交换机，面试必背：

| 类型 | 匹配规则 | 典型用途 |
|---|---|---|
| `direct` | routing key 完全相等 | 按订单状态、按错误级别分发 |
| `topic` | 以 `.` 分词，`*` 匹配**一个**词，`#` 匹配**零个或多个**词 | `order.paid.cn`、`order.created` 这类分级事件 |
| `fanout` | 忽略 routing key，广播给所有绑定队列 | 一份事件多种用途（缓存刷新 + 审计 + 通知） |
| `headers` | 按消息 header 的键值对匹配（`x-match=all/any`） | 少用，匹配性能比 topic 差 |

### 为什么
把「谁产生事件」和「谁关心事件」彻底解耦：新增一个下游，只要加一条 Binding，生产者一行代码都不用改。但它和 Kafka 不是一套模型：Kafka 是 **Topic / Partition / 消费组 + 位点回溯**，消息消费后仍保留；RabbitMQ 是 **Exchange / Queue / 逐条 ack 后删除**，更擅长业务事件与复杂路由，不擅长日志流回放。

### 怎么用
- 业务事件用 `topic`，队列用业务语义命名（如 `order.pay.sms`），binding key 用 `order.paid.*`。
- 声明（`queueDeclare` / `exchangeDeclare`）要**幂等且参数完全一致**：同名队列第二次用不同参数声明会直接报 `PRECONDITION_FAILED` 并断连。
- 生产端复用 Connection/Channel；每次发消息新建 TCP 连接是典型性能事故。

### 常见坑
- 以为「消息发给 Exchange 就存下来了」：如果没有任何队列按规则绑定到这个 Exchange，消息会被直接丢弃（可开 `alternate-exchange` 兜底，或开 publisher confirm 的 `ReturnCallback` 感知不可路由）。
- 拿 `*` 当通配所有层级：`order.*` 匹配不了 `order.paid.cn`，那要用 `order.#`。
- 把 RabbitMQ 当 Kafka 用，指望消费完还能按位点重放历史消息。

### 面试怎么问
「一条消息怎么被多个系统消费？」——答 fanout / 多个 binding 让消息进多个队列，每个队列一份拷贝；再补「同一个队列内是竞争消费，一条消息只给一个消费者」，层次就出来了。

## 可靠投递：持久化、Confirm 与手动 ACK

### 是什么
「不丢消息」是三段责任链，缺一段都不成立：

1. **Broker 落盘三件套**：Exchange `durable=true`、Queue `durable=true`、消息 `deliveryMode=2`（persistent）。只声明 durable 队列而消息不设持久化，重启后队列还在、消息没了。
2. **生产端确认**：`publisher confirm`（`ConfirmCallback`）异步告知消息是否被 Broker 正确接收；不可路由的消息还要靠 `ReturnCallback`（`mandatory=true`）兜住。AMQP 事务 `txSelect/txCommit` 是同步阻塞的，吞吐会掉一个数量级，生产上基本不用。
3. **消费端确认**：关闭 `autoAck`，业务**处理成功后**再 `basicAck`；失败 `basicNack` / `basicReject` 并配合重试队列、死信队列。`basic.qos(prefetchCount)` 限制该消费者上**未 ack 的消息数**，避免慢消费者把消息全捞到手里。

### 为什么
端到端实际能廉价保证的是**至少一次**：confirm 回调前生产者宕机、ack 之前消费者宕机，都会造成重投。所以「至少一次 + 消费端幂等」才等价于业务上的恰好一次。幂等用业务流水号做去重表 / 唯一索引，且「查重 → 执行业务 → 记已处理」三步必须在**同一个本地事务**里。

### 怎么用
- 订单这类核心链路：`本地消息表（outbox）` 保证「业务落库」与「待发消息」原子，再由投递任务扫描发送，confirm 只用来回写状态；这比「事务里直接发 MQ」可靠得多。
- 消费失败分级：可重试的进重试队列（带重试次数），多次失败进死信队列并告警，人工可重放。
- `prefetch` 一般先给 10～50，结合单条耗时与实例数压测调整，不是越大越好。

### 常见坑
- `autoAck=true`：Broker 一投递就当成功，消费者处理到一半崩溃，消息永久丢失。
- 失败就 `requeue=true` 无限重试：一条毒消息反复循环，CPU 打满、正常消息饿死。
- 只开 confirm 就宣称「绝不丢」：confirm 只证明 Broker 收到了，不保证已落盘（还要持久化三件套），也不覆盖生产者本地事务与消息不同步的问题。
- `prefetch` 设成几千：单个消费者堆大量 `unacked`，负载不均、内存上涨，实例重启后这批消息全部重回队列造成重复洪峰。

### 面试怎么问
「怎么保证消息不丢？」按生产端 / Broker / 消费端三段答，最后一定补「但至少一次会带来重复，幂等要落在业务层」，这才是完整答案。

## 死信、延迟、堆积与高可用队列

### 是什么
**死信交换机（DLX）** 接收三类消息：消费者 `reject/nack` 且 `requeue=false`、消息 TTL 过期、队列达到 `x-max-length` 被挤出的队头消息。配合 `x-dead-letter-exchange` 与 `x-dead-letter-routing-key` 使用。

**延迟队列**常见做法是 `TTL + DLX`：消息先发到无消费者的缓冲队列，过期后由 DLX 转到真正消费的队列。也可以用官方插件 `rabbitmq_delayed_message_exchange`（延迟在交换机层按消息 `x-delay` 定时），或干脆用 Redis ZSet / 定时扫表做外部调度。

**高可用队列**：经典**镜像队列（mirrored queue）已废弃并在 RabbitMQ 4.x 移除**，现在推荐**仲裁队列（Quorum Queue）**——基于 Raft 复制，通常 3 或 5 个副本，优先保证数据安全与故障自动恢复；代价是不支持部分经典队列特性（消息级 TTL 策略、优先级、部分非持久化消息语义），单队列吞吐也受 Raft 顺序复制限制。

### 为什么
- TTL 有个非常隐蔽的坑：RabbitMQ 只在**消息到达队头**时才检查是否过期。若队列里第一条是 30 分钟后才过期的消息，后面 10 秒就该过期的消息会被一直堵住。所以「按延迟档位拆成多个队列」（10s / 1min / 10min）比一个混合 TTL 队列可靠。
- 堆积不是靠「加机器」万能解决的：要看 `ready` 与 `unacked` 的比值、单条消费耗时、下游依赖容量。

### 怎么用
- 监控四件套：`ready`（待投递）、`unacked`（已投递未确认）、投递/确认速率、消费耗时与错误率；DLQ 必须有消费与告警，不能只堆着。
- 堆积处置顺序：先看是不是消费端变慢 / 下游超时 → 再优化单条耗时（异步化、批量化、加缓存）→ 核对下游能承受的并发 → 最后才扩容消费者，并用多队列拆分单队列吞吐上限。
- 临时兜底可把消息转储到外部存储再回放，但**严禁直接清空队列**（等于丢业务数据）。
- 集群至少 3 节点、Quorum Queue 副本数取奇数；网络分区策略结合业务在 `pause-minority` / `autoheal` 之间明确选择，别用默认值碰运气。

### 常见坑
- 一个队列混用不同 TTL 的延迟消息，出现「后面的短延迟消息迟迟不生效」。
- DLX 配了却没人消费、没告警，死信变成「第二个垃圾场」。
- 把 `ready` 上涨当成 Broker 写盘慢，去关持久化——既治不了堆积，又引入丢消息风险。
- 以为 `durable=true` 就等于高可用：持久化只保证**单节点重启**后消息还在，节点磁盘损坏或整机宕机仍需副本。

### 面试怎么问
「消息堆积几百万条怎么排查？」按「先看 ready/unacked 与单条耗时 → 定位下游 → 优化单条 → 核对下游容量 → 再扩容 → 兜底转储」这条链答，并主动说明「不能直接清队列、不能盲目调大 prefetch」。

## 动手清单

### 练习 1：把 topic 路由规则跑一遍
建一个 `topic` 交换机，分别用 `order.*` 与 `order.#` 绑定两个队列，依次发送 `order`、`order.created`、`order.paid.cn`、`payment.created`，记录每个队列收到了哪些消息，用自己的话解释 `*` 与 `#` 的差别。

### 练习 2：做一次「不丢消息」的完整配置
写出 Exchange / Queue / 消息的持久化三件套配置，开启 publisher confirm 与 `ReturnCallback`，消费端改手动 ack 并设置 `prefetch=20`；再故意让消费者在处理中抛异常，观察 `unacked`、重试与死信队列的变化。
**自测标准**：能说清「confirm 保证到 Broker」和「消息已落盘」不是一回事，以及为什么还必须做消费端幂等。

### 练习 3：复现延迟队列的队头阻塞
用 `x-message-ttl` + DLX 建一个缓冲队列，先发一条 30 分钟过期的消息，再发一条 10 秒过期的消息，观察第二条是否被堵住；改成按延迟档位拆成两个队列，或换用延迟消息插件，对比效果。

### 练习 4：写一份堆积排查清单
针对「ready 持续上涨、unacked 顶到 prefetch 上限、消费者 CPU 很低」的场景，写出至少 4 步排查动作与每一步要看的指标，并说明为什么不能直接清队列、为什么不能盲目扩容。
**自测标准**：能完整说出 AMQP 四种 Exchange 的匹配规则、可靠投递三段责任链、DLX 的三种来源，以及 Quorum Queue 与镜像队列的取舍。
