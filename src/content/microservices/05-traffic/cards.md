# 05 流量治理与高可用交付

## 限流算法：令牌桶、漏桶与滑动窗口

### 是什么
- **固定窗口**：每分钟一个计数器，简单但存在**临界突刺**——59 秒和 00 秒各放 100 个请求，实际一秒内过了 200 个。
- **滑动窗口**：把窗口切成多个小格分别计数，按时间加权求和，削掉临界突刺，代价是存储更多计数。
- **漏桶**：请求进水、以恒定速率出水，超出桶容量就拒绝，输出**绝对平滑**，但不允许突发。
- **令牌桶**：以固定速率往桶里放令牌，请求取到令牌才放行，桶里攒下的令牌允许**一定突发**，是网关限流最常用的一档。

### 为什么
限流的目的不是「把 QPS 压到某个数字」，而是**让系统只承接自己处理得了的量**，超出部分快速失败或排队，避免雪崩。不同算法的区别在于「允许多大的突发」和「实现成本」。

### 怎么用
- 网关层按「接口 + 应用 + 用户」多维度限流，核心交易接口单独设阈值，别用全局一个值。
- Spring Cloud Gateway 用 `RequestRateLimiter` + Redis 令牌桶；Sentinel 支持按资源、按来源与热点参数限流。
- 超限返回 429 + `Retry-After`，让调用方知道多久后重试；同时区分「拒绝」与「排队」，非核心链路可直接降级。

### 常见坑
- 用固定窗口限流却以为「每分钟 100」就安全，忽略了窗口交界处的双倍流量。
- 只做单机限流：10 个实例各限 100 QPS，网关总入口实际能进 1000 QPS，下游照样被打挂。
- 限流阈值拍脑袋定，没用压测得到的容量做依据，大促时要么误伤正常流量要么没挡住。

### 面试怎么问
「令牌桶和漏桶的区别？」答「漏桶恒定速率、不允许突发；令牌桶允许攒令牌应对突发」，再补一句固定窗口的临界突刺与滑动窗口的解法，基本就是完整答案。

## 从单机限流到分布式限流

### 是什么
单机限流（Guava RateLimiter、Semaphore）只在**本进程内**计数，多实例部署时总阈值 = 单机阈值 × 实例数，且扩缩容会改变总阈值。分布式限流把计数放到共享存储（Redis），让所有实例对同一个 key 原子计数，通常用 **Lua 脚本**把「读计数 → 判断 → 自增 → 设过期」包成一次原子操作。

### 为什么
限流口径必须统一在「被保护的资源」上，而不是「某台机器」上。下游数据库只有一份，它承受的是所有实例加起来的流量。

### 怎么用
- Redis + Lua：`INCR key` 后第一次设置 `EXPIRE`，或用令牌桶脚本按时间戳补充令牌；Lua 保证多实例并发下不会超发。
- Redis 成为瓶颈时，用「本地配额 + 中心批量预取」：每个实例一次领一批令牌，减少访问 Redis 的次数。
- 限流规则放配置中心，支持大促期间动态调阈值与一键关闭，不要写死在代码里。
- 观测三件套：放行量、拒绝量、拒绝率，配合下游 RT 与错误率验证阈值是否合理。

### 常见坑
- `INCR` 与 `EXPIRE` 分成两条命令：进程在中间崩溃会留下永不过期的 key，计数满后流量被永久拒绝。
- 限流 key 只按接口取名，导致某个大客户把整条接口的配额吃光，应支持按调用方细分。
- 把限流当唯一手段：没有超时、熔断、降级与容量评估，限流只能拖延雪崩，救不了慢查询。

### 面试怎么问
「10 台机器怎么限总流量 1000 QPS？」答 Redis 集中计数 + Lua 原子，再提本地配额优化与「限流不是万能的」，能体现真实落地经验。

## 灰度发布与容量评估

### 是什么
**灰度（金丝雀）发布**先让新版本承接一小部分流量，观察错误率、RT、业务指标，再逐步放量；出问题按比例回退即可，爆炸半径远小于全量发布。**蓝绿部署**准备两套完整环境，靠路由整体切换，回滚快但资源翻倍。

**容量评估**是回答「这台系统到底能扛多少」：通过单接口压测找到拐点（RT 陡增、错误率上升时的 QPS），按峰值流量留 2～3 倍余量，再推导需要的实例数、连接池大小与缓存容量。**全链路压测**则在生产或影子链路里模拟真实大促流量，验证的是整条链路（网关 → 服务 → 缓存 → 数据库），而不只是单接口。

### 为什么
绝大多数线上事故来自「变更」和「容量」：代码没问题的发布也可能因为连接池、慢 SQL、缓存命中率而崩。灰度控制变更风险，压测提前暴露容量短板。

### 怎么用
- 灰度维度按用户 ID / 租户 / 地域哈希，保证同一用户始终命中同一版本，避免会话在版本间跳。
- 灰度期盯四类指标：错误率、P99 延迟、下游依赖耗时、核心业务转化；任一异常立即停止放量。
- 压测数据要隔离（影子表 / 影子库 / 压测标识透传），严禁污染生产数据与统计口径。
- 发布前准备回滚预案，回滚要演练过，不能只写在文档里。

### 常见坑
- 灰度按随机百分比切流量，同一用户两次请求落到不同版本，出现「时好时坏」的诡异现象。
- 只压单接口就宣布「系统能扛 1 万 QPS」，忽略数据库连接池、缓存带宽与下游限流这些共享瓶颈。
- 压测流量写进生产表，事后数据对不上，报表与结算全被污染。

### 面试怎么问
「新版本上线怎么保证不出事？」按灰度切流 → 观测指标 → 逐步放量 → 一键回滚四步答，再补「容量来自压测而不是拍脑袋」，就很扎实。
