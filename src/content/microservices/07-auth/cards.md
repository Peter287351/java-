# 07 统一认证授权：JWT、OAuth2 与 SSO

## JWT：自包含令牌与验签

### 是什么
**JWT（JSON Web Token）** 是一段自包含的令牌，形如 `xxxxx.yyyyy.zzzzz`：

| 段 | 内容 | 说明 |
|---|---|---|
| Header | `alg`（如 RS256）、`typ`、`kid` | 声明签名算法与密钥标识 |
| Payload | `sub`、`iss`、`aud`、`exp`、`iat`、`jti`、自定义 claim | 存放身份与授权信息 |
| Signature | 对前两段的签名 | 防篡改 |

三段都是 **Base64URL 编码，不是加密**：任何人拿到 token 都能解出 payload 里的明文，所以绝不能放密码、身份证、手机号等敏感数据。服务端不存会话，靠**验签**确认令牌是自己签发且未被改动，这就是「无状态」。

`HS256` 是对称算法（所有服务共享同一密钥，谁能验签谁就能签发）；`RS256` / `ES256` 是非对称算法（认证中心用私钥签，业务服务只拿公钥验），微服务场景更推荐后者。

### 为什么
传统 Session 需要服务端共享存储（Redis / Session 复制），跨系统、跨域名时很重。JWT 把状态放进令牌本身，网关或任一服务本地验签即可放行，天然适合多服务、多端的统一认证。代价是**签发后难以立刻作废**。

### 怎么用
- 验签必须做全：校验签名算法在白名单内（禁止接受 `alg=none`、禁止 RS256 与 HS256 混淆）、校验 `exp`/`nbf`、`iss`、`aud`，必要时校验 `jti` 防重放。
- `access_token` 短有效期（5～30 分钟）+ `refresh_token` 长有效期且只发给认证中心、可轮换可吊销；刷新时校验 refresh token 未被使用过（轮换检测重放）。
- 需要「改密码后立刻踢下线」这类即时吊销时，用三选一或组合：短有效期 + 主动刷新、Redis 黑名单（按 `jti` 存到原 exp 为止）、用户令牌版本号（`token_version` 变更后旧 token 全部失效）。
- 传输只走 HTTPS，优先放 `Authorization: Bearer`；放 localStorage 要评估 XSS 风险，敏感场景用 `HttpOnly + Secure + SameSite` Cookie。

### 常见坑
- 以为 Base64URL 就是加密，把敏感信息塞进 payload。
- 只验签名、不验 `exp` / `aud` / `iss`：过期令牌、别系统签发的令牌照样放行。
- 信任客户端传来的 `alg`，导致算法混淆攻击（把 RS256 改成 HS256，用公钥当 HMAC 密钥伪造签名）。
- 密钥硬编码在代码仓库、所有服务共用一把 HS256 密钥：任一服务泄露，全站可伪造令牌。
- 「退出登录」只在前端删 token，后端令牌在有效期内仍然可用。

### 面试怎么问
「JWT 怎么注销？」先说无状态导致不能像 Session 那样直接删，再给短有效期 + 黑名单 / 令牌版本号 / refresh 轮换这几种工程折中，最后点出「能接受秒级延迟就别引入中心状态」，这层次就完整了。

## OAuth2、OIDC 与单点登录

### 是什么
**OAuth2 是授权框架，不是认证协议**：解决的是「第三方应用在不拿用户密码的前提下，获得对资源的有限访问权」。四个角色：`Resource Owner`（用户）、`Client`（应用）、`Authorization Server`（认证中心）、`Resource Server`（业务 API）。授权结果是带 `scope` 的 access token。

四种授权模式里，现在真正推荐的是两种：

| 模式 | 适用 | 要点 |
|---|---|---|
| 授权码 + PKCE | Web 应用、SPA、移动端（当前默认推荐） | 先拿一次性 code，再用 `code_verifier` 换 token；code 被截获也换不到令牌 |
| 客户端凭证 | 服务间调用（无用户参与） | `client_credentials`，按 client 身份与 scope 授权 |

`implicit`（隐式）与 `password`（密码）模式已不推荐：前者把 token 暴露在 URL 片段里，后者要求应用直接接触用户密码。

**OIDC** 是 OAuth2 之上的身份层：多返回一个 `id_token`（JWT），明确回答「你是谁」，配合 `/userinfo` 拿到用户资料；只谈 OAuth2 而直接拿 access token 当用户身份，是常见设计错误。**SSO（单点登录）** 是产品形态：一个统一认证中心 + 各系统共享登录会话，用户在一个系统登录后访问其他系统不必再输密码，底层通常用 OIDC / CAS / SAML 实现。

### 为什么
把「登录」这件事从每个业务系统里抽出来集中做：密码策略、MFA、风控、审计、改密与踢下线只有一处实现；业务系统只认令牌，不再各自存密码。

### 怎么用
- 网关或各服务校验 `scope`（能做什么）与 `aud`（这个 token 是签给谁的），别把 scope 和用户角色混为一谈。
- 角色 / 权限属于业务内授权（RBAC），由资源服务自己判定；token 里只放稳定、少量、不易变的身份信息，避免权限一改就得重签所有令牌。
- 服务间调用用 `client_credentials` 拿服务令牌，并在网关剥离外部传入的同名身份头，防止伪造。
- 统一登出要同时清认证中心会话、各系统本地会话与 refresh token，否则「退出了但换个系统还能进」。

### 常见坑
- 用 `password` 模式让自家 App 收集用户密码，等于把密码扩散到客户端。
- 拿 access token 当用户身份证明（应该用 OIDC 的 id_token）。
- 授权码模式不加 PKCE、不校验 `state`，留下授权码拦截与 CSRF 风险。
- 把 refresh token 也下发给浏览器前端长期保存，泄露后可长期换取新 access token。

### 面试怎么问
「OAuth2 和 JWT 什么关系？」——OAuth2 是流程与角色规范，JWT 是令牌的一种格式，两者不在同一层；再补「OAuth2 管授权、OIDC 管认证」，基本就是标准答案。

## 网关统一鉴权与 RBAC

### 是什么
**统一鉴权**通常放在网关：校验签名、`exp`、黑名单、必要 scope，失败直接返回 401；通过后再把可信的用户身份（userId / tenantId）放进内部 Header 传给下游。

**RBAC** 是业务内的授权模型：`user → role → permission` 三张表 + 两张关联表，permission 可以细到菜单、接口（HTTP 方法 + 路径）、数据范围（本人 / 本部门 / 全公司）。Spring Security 侧对应过滤器链、`SecurityContext` 与 `@PreAuthorize`。

### 为什么
网关做「是不是合法用户」，业务服务做「这个用户能不能干这件事」，两层职责不能互相替代：网关不知道订单接口的业务规则，业务服务也不该每个都重复实现验签。同时**内网不能全盲信**：网关被绕过、内部直连、服务间调用都可能让未校验请求进入，所以下游至少要做最小校验（内部令牌 / mTLS / 签名复核）。

### 怎么用
- 网关入口**先删除**外部请求里所有同名身份 Header（如 `X-User-Id`），再由网关重新写入，防止客户端伪造身份。
- 区分 401（未认证 / 令牌无效）与 403（已认证但无权限）；越权分两类：水平越权（改 id 看别人的数据）、垂直越权（普通用户调管理员接口），都必须在服务端按当前登录人做数据归属校验。
- 敏感操作（改密、支付、导出）二次校验、写审计日志（谁、何时、对什么资源、结果）。
- 权限变更要有缓存失效机制，避免给用户加了角色却半小时不生效，或者移了权限仍能访问。

### 常见坑
- 「网关验过 Token 了，下游完全信任 Header」：一旦有内部直连或网关配置漏了路径，就能直接伪造任意用户。
- 只做菜单级权限，接口不校验，抓包改个 URL 就拿到别人数据。
- 把角色写死在 JWT 里且有效期很长，降权后旧令牌依然带着管理员角色。
- 用 403 表示「没登录」，前端据此不跳登录页，用户一直卡在空白页。

### 面试怎么问
「登录以后怎么防越权？」按「网关验签 → 下游最小校验 → 业务层按登录人校验数据归属 → 接口级与数据级权限 → 审计」答，并主动区分 401 / 403 与水平 / 垂直越权。

## 动手清单

### 练习 1：拆一个 JWT
自己生成一个 RS256 的 JWT，把三段分别 Base64URL 解码，写出 header 与 payload 的内容；然后改掉 payload 里的 `sub` 再发给本地验签接口，观察是否被拒绝，并说明「能解码」与「能伪造」的区别。

### 练习 2：走一遍授权码 + PKCE
用本地认证中心跑一次授权码流程，记录 `code_challenge`、`code_verifier`、`state`、`code`、`access_token`、`id_token` 的出现顺序，说明如果授权码在回调阶段被截获，攻击者为什么仍然换不到令牌。

### 练习 3：设计一张权限表
为一个「订单管理系统」画出 RBAC 的表结构，给出至少 3 个接口级权限与 1 个数据范围权限；再写出「网关已验签，但用户改 URL 里的订单 id 查到别人订单」的修复方案。
**自测标准**：能说清 JWT 三段与验签要校验哪些 claim、OAuth2 与 OIDC 的分工、授权码 + PKCE 为什么安全、以及网关鉴权与业务授权的边界。
