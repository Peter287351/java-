## 把日志当表来查

### 是什么
结构化的请求日志可以看成一张表：`ts`（时间）、`service`（服务）、`level`（级别）、`status`（HTTP 状态码）、`latency_ms`（耗时）、`trace_id`（链路）、`version`（发布版本）。用 SQL 做聚合，比肉眼翻日志快得多。

### 怎么用
四步定位：按服务聚合看谁报错多（`GROUP BY service` + `COUNT`）→ 按分钟分桶找峰值（`substr(ts,1,16)`）→ 找最慢请求（`ORDER BY latency_ms DESC LIMIT 3`）→ 按版本关联发布记录（`JOIN deploy ON service + version`）。

### 常见坑
- 只筛 `level = 'ERROR'` 会漏掉「状态码 5xx 但日志级别是 WARN」的请求。
- 时间桶要用字符串前缀或 `substr`，TEXT 时间格式 `YYYY-MM-DD HH:MM:SS` 可直接比较。
- 找峰值别用 `LIMIT 1`，并列分钟会被漏掉，用 `= MAX(cnt)` 或 `RANK()`。

### 面试怎么问
「线上报错变多，怎么用 SQL 定位？」答先按服务聚合、再按时间分桶、然后对齐版本与慢请求。

## 与手写 SQL 修炼场的对应关系

### 是什么
本站「手写 SQL 修炼场」的运维数据集（service_log / deploy / heartbeat）就是一张迷你的故障现场：09:05 发布 order v2 后 5xx 激增，可以从六个角度查出同一结论。

### 怎么用
建议按顺序练：错误最多的服务 → 各服务 5xx 错误率 → 5xx 最密集的分钟 → 最慢的 3 条请求 → 哪个发布版本错误最多 → 哪台机器心跳异常。每一步的答案都指向「v2 发布引入故障，应回滚」。

### 常见坑
- 算比率时忘了乘 100.0，整数除法会把错误率算成 0。
- 关联发布表只按 service 不按 version，会把所有版本的错误算到每次发布上。
- 查心跳只看「状态非 OK」，会把曾经抖动但已恢复的机器误报成故障。

### 面试怎么问
「怎么证明该回滚哪个版本？」答按 service + version 关联错误日志，比较各版本错误数，并结合发布时刻验证。
