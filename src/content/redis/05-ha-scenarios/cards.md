## 高可用与典型场景选型

### 是什么
- **主从复制**：从库执行 `psync`，全量（RDB + 缓冲区）+ 增量（repl_backlog 环形缓冲）。主从异步复制 → 存在延迟窗口。
- **哨兵（Sentinel）**：监控（主观下线 → 询问其他哨兵达成客观下线）→ 选主（Raft 式投票选 leader 哨兵）→ 从节点中按优先级/偏移量提升新主 → 通知客户端。
- **Cluster**：16384 个哈希槽按 `CRC16(key) % 16384` 分布，每个主节点负责一段槽；客户端可重定向（MOVED/ASK）。

### 为什么
哨兵解决"主挂了谁来顶、怎么让客户端知道"；Cluster 解决"单机内存/写瓶颈"，同时内置故障转移。读写分离：读走从库要接受延迟。

### 怎么用
- 大 key 治理：拆 key（Hash 分片）、压缩 value、删除用 `UNLINK`（异步）。
- 热 key：本地缓存（Caffeine）+ key 加随机后缀多副本。
- 排查工具：`redis-cli --bigkeys` / `--hotkeys`、慢日志 `SLOWLOG GET`。

### 常见坑
- Cluster 模式下多 key 命令（MGET/事务/Lua）要求 key 在同一槽：用 hash tag `{user1001}` 强制同槽。
- 主从延迟下的读分离要评估业务容忍度。

### 面试怎么问
「哨兵和 Cluster 选哪个？」——数据量单机能装、要高可用 → 主从+哨兵；容量/写并发超单机 → Cluster。

## 动手清单

1. 本地起 1 主 2 从 + 3 哨兵（配置文件各 10 行），kill 主库观察故障转移与客户端重连。自测标准：能说出客观下线的仲裁条件。
2. 用 `redis-cli --bigkeys` 扫描生产只读实例，找出 Top10 大 key 并给出治理方案。自测标准：至少说出两种拆分或异步删除手段。
