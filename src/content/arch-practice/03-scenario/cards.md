# 03 真实场景：技术栈与架构选型

## 先读约束，再选技术：四把尺子

### 是什么
架构题没有「最好的技术」，只有「在这组约束下最合适的取舍」。拿到需求先量四把尺：
1. **容量**：日活多少、峰值 QPS、数据量、读写比。峰值 500 QPS 与 5 万 QPS 是两种系统。
2. **一致性**：哪些数据错了会造成资损或纠纷（名额、金额、库存），哪些允许分钟级延迟（报表、统计、通知）。
3. **团队与工期**：3 人 4 周和 30 人半年，能驾驭的组件数量完全不同；每多一个中间件就多一份部署、监控、排障与值班成本。
4. **运维与预算**：只有一台 4C8G、无人专职运维时，Kafka + Elasticsearch + K8s 这类需要集群的组件直接出局，不是技术不行，是养不起。

### 为什么
实习生最容易掉的坑是「把大厂架构当成标准答案」：看到高并发就上微服务、Kafka、分库分表，却没注意人家的规模、团队和 SRE 配置。技术选型的本质是**成本与风险的匹配**，多引入一个组件必须换来明确的收益，否则就是净负债。

### 怎么用
- 把约束写成一句可验证的话：「3 人 / 4 周 / 1 台 4C8G / 峰值 500 QPS / 名额不能超 / 数据不能丢」，然后逐条检验候选方案。
- 单体 + 单机关系型数据库能吃下的量远超直觉：索引合理、连接池得当，单实例几百 QPS 很轻松，别急着拆。
- 硬约束优先于优雅：不能超名额就留在**一个本地事务**里用原子 SQL 解决，别把强一致需求拆到跨服务链路。

### 常见坑
- 用「以后可能要扩展」为当下的过度设计辩护：未来流量真来了再演进，届时你有真实数据与预算，判断比现在准得多。
- 把「允许延迟」当成「可以丢数据」：统计慢几分钟没关系，但报名记录一条都不能少，这两件事要分开设计。
- 只在应用层做防重（前端禁用按钮、接口查一遍再插入），没在数据库加唯一索引兜底，并发下必出超卖。

### 面试怎么问
「给你一个 XX 系统，怎么设计？」先反问容量、一致性、团队与工期，再给方案并主动说明「为什么不用更重的方案」，比直接报组件名得分高得多。

## 从单体开始：什么时候才该拆

### 是什么
**演进式设计**：先用模块化单体起步（按业务域分包、接口清晰、数据访问收敛），把监控、日志、备份、幂等这些地基打好；等出现明确信号再拆——某块功能的发布频率/伸缩需求/故障隔离要求明显不同，团队规模大到多人改同一处互相阻塞，或单库容量真的触顶。

### 为什么
分布式不会消灭复杂度，只会把它从「代码里」搬到「网络里」：一次本地事务变成跨服务一致性、一次方法调用变成超时重试与幂等、一个堆栈变成跨机链路追踪。在没拿到拆分收益之前先付这些成本，是净亏。

### 怎么用
- 想解耦先解耦代码（模块边界、接口抽象），不必先解耦部署。
- 非核心链路要异步，先用数据库 outbox 表 + 定时任务，比上 MQ 便宜得多；量起来了再换。
- 缓存只用在读多写少、且能容忍短暂不一致的数据上；名额、余额这类强一致数据别放缓存里算。

### 常见坑
- 拆了服务但共用一个库：既没拿到独立伸缩，又丢了本地事务，是最糟的中间态。
- 用 Saga / 补偿事务去实现一个本可以单库原子扣减的名额限制，把简单问题变复杂还更难保证正确。
- 单机部署却不做备份与恢复演练：「数据不能丢」是运维要求，不是代码要求。

### 面试怎么问
「什么时候考虑拆微服务？」答出触发信号（发布节奏、伸缩、隔离、团队规模）与「先单体后演进」的路径，再补一句分布式带来的三类新成本，基本就是有实战感的答案。

## 动手清单

### 练习 1：给约束排优先级
拿本章题目里的场景，把 6 条约束按「违反后果严重程度」排序，写出哪两条决定了必须保留本地事务、哪一条允许引入异步。

### 练习 2：写一条原子扣减 SQL
设计报名表与名额表，写出 `UPDATE ... SET remain = remain - 1 WHERE remain > 0` 并说明返回影响行数为什么能防超卖；再补一个 `(activity_id, user_id)` 唯一索引防重复报名。

### 练习 3：说清「为什么不用」
针对同一场景，用两句话分别说明「为什么不上 Kafka」「为什么不上微服务」，要求给出成本理由而不是「用不上」。
**自测标准**：能在 3 分钟内讲清一组约束下的技术栈选择，并主动说出被否决方案的代价。
