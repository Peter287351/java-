# 01 消息队列

## MQ 解决什么，代价是什么

### 是什么
消息队列把「调用方直接等被调用方」改成「调用方投递消息后就返回，消费方按自己节奏取」。三件事最典型：**解耦**（新增下游不用改上游代码）、**异步**（短信、积分、报表不必卡在主链路）、**削峰**（突发流量先落在 Broker，消费端匀速消化）。代价是引入**最终一致性**、消息可能重复或乱序、多一个必须高可用运维的组件，以及排障链路变长。

### 为什么
同步链路的可用性是各环节的乘积：主链路上挂一个非核心的下游，整体可用性就被它拖下去。把非核心步骤移出主链路，等于把「木桶短板」从关键路径上拿掉。但注意这不是免费的——原本一个本地事务就能保证的事，现在要跨系统协调。

### 怎么用
- 判断标准很简单：**这个步骤失败，用户这次操作要不要跟着失败？** 不要，且允许延迟 → 适合异步；要，且必须立刻一致 → 留在同步事务里。
- 小体量、低 QPS、没有专职运维的项目，用数据库表 + 定时扫描（outbox 模式）往往比上 Kafka 更划算。
- 主题/队列按业务域划分，消息体带唯一业务 ID 与版本号，方便幂等和后续演进。

### 常见坑
- 「为了显得架构先进」硬上 MQ：一个日活几百的内部系统引入 Kafka + ZK，运维成本远超收益。
- 以为 MQ 保证 exactly-once，业务层不做幂等：网络抖动、消费者重启都会重复投递，重复扣款就是这么来的。
- 把核心一致性交给消息：下单扣库存必须同步确认，不能「发条消息然后祈祷消费成功」。

### 面试怎么问
「为什么要引入消息队列？」按解耦/异步/削峰三点答，然后**主动补代价与规避**（重复消费靠幂等、最终一致性靠对账、可用性靠集群与监控），比只背三个词高一个档次。

## 不丢消息与幂等：三段式责任链

### 是什么
消息从生产到消费经过三段，每段都可能丢：
1. **生产端**：发送后要等 Broker 的 ack / confirm，失败要重试；更好的是**事务消息**或**本地消息表（outbox）**，保证「业务数据落库」与「消息发出」要么都成、要么都不成。
2. **Broker**：开启持久化、副本数 ≥ 2、acks=all，避免单机宕机丢数据。
3. **消费端**：关闭自动 ack，业务处理成功后再手动提交位点；处理失败进重试队列，多次失败进死信队列并告警。

**幂等**在消费端落地：唯一键去重表 / 数据库唯一索引 / Redis SETNX，用业务流水号而不是消息 ID 做键（重试后消息 ID 可能变）。

### 为什么
「最多一次、至少一次、恰好一次」里，分布式系统实际能廉价拿到的是**至少一次**；既然重复不可避免，就让消费逻辑幂等，从而把「至少一次 + 幂等」等价于业务上的恰好一次。

### 怎么用
- 顺序性只在**分区/队列内**成立：同一业务实体（如同一订单）用同一个 key 做路由，才能保序；别指望全局有序。
- 消费逻辑写成「先查幂等表 → 再执行业务 → 同一事务里记录已处理」，三步在一个本地事务内。
- 堆积告警看 lag（未消费条数）与消费耗时，扩容消费者数不能超过分区数。

### 常见坑
- 先提交位点再处理业务：处理中宕机，消息永久丢失。
- 用 `auto.offset.reset=earliest` 当成「不丢消息」的手段：这只是位点策略，与可靠性无关。
- 死信队列没人看：消息安静地堆着，业务数据悄悄少了。

### 面试怎么问
「如何保证消息不丢、不重？」分三段答责任链，再明确「不重」靠消费端幂等而非 MQ 承诺，最后提对账兜底，链路就完整了。

## 动手清单

### 练习 1：画一次失败链路
在纸上画出下单成功后发券的链路，标出「业务库已提交但消息发送失败」「消息已投递但消费重试导致重复」两处断点，并写出对应的 outbox 与幂等方案。

### 练习 2：写一段幂等消费
用一张 `consumed_msg(biz_id PRIMARY KEY)` 表，实现「插入成功才执行业务、业务与插入在同一事务」的消费逻辑。
**自测标准**：能说清引入 MQ 的三个收益与三个代价，能按生产/Broker/消费三段列出不丢消息的措施。
