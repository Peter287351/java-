# 03 HTTP / TCP 与操作系统

## TCP：三次握手、四次挥手与 TIME_WAIT

### 是什么
建立连接用**三次握手**：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK。目的是让双方各自确认「自己的发送、自己的接收、对方的发送、对方的接收」都正常，并同步初始序列号。关闭用**四次挥手**，因为 TCP 全双工、一方发 FIN 只表示「我没数据要发了」，仍可能要收对方数据，所以两个方向要分别关闭。主动关闭方最后进入 **TIME_WAIT**，停留 2MSL。

### 为什么
两次握手无法让服务端确认客户端的接收能力，历史重复 SYN 还可能被误当成新连接。TIME_WAIT 有两个作用：保证最后一个 ACK 能到达（丢了就重发 FIN），以及让本次连接的残留报文在网络中消散，避免污染使用相同四元组的新连接。

### 怎么用
- 压测时看到大量 TIME_WAIT 多在**主动关闭方**：优先让客户端复用连接（HTTP Keep-Alive / 连接池），而不是急着调内核参数。
- 短连接高并发容易耗尽本地端口（约 2.8 万个可用 ephemeral port），表现是 `Cannot assign requested address`。
- 排查用 `ss -antp`、`netstat -s`、`tcpdump -i any port 8080`。

### 常见坑
- 以为 TIME_WAIT 是「服务端的状态」：谁主动关谁进，与客户端/服务端角色无关。
- 一见 TIME_WAIT 就开 `tcp_tw_reuse` / 调小 `tcp_fin_timeout`：NAT 环境下可能引发连接串扰，先查是不是没用连接池。
- 把 `connection refused` 和 `connection timeout` 混为一谈：前者是对端明确回 RST（端口没监听），后者多半是包被防火墙丢弃或路由不通。

### 面试怎么问
「为什么是三次不是两次？」答出「防止历史重复连接初始化 + 双方都要确认收发能力」；再被追问 TIME_WAIT 就答 2MSL 的两个理由，链路很完整。

## HTTP：状态码、幂等与连接复用

### 是什么
HTTP 是无状态的请求-响应协议，方法语义里 **GET / PUT / DELETE 幂等**（重复执行效果相同），**POST 非幂等**（重复提交可能创建多笔订单）。状态码分五类：2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错。常见易混：`401` 未认证、`403` 已认证但无权限；`301` 永久重定向（浏览器会缓存）、`302` 临时；`304` 协商缓存未变更、不返回响应体；`502` 网关拿到上游无效响应、`504` 网关等上游超时。

### 为什么
幂等性是重试设计的基础：网络抖动时，只有幂等请求才能安全自动重试。连接复用（Keep-Alive / HTTP/2 多路复用）则省掉反复三次握手与 TLS 握手的 RTT 开销。

### 怎么用
- 写操作要防重复提交：前端禁用按钮只是体验层，服务端要用唯一业务流水号 + 数据库唯一索引或幂等表兜底。
- 调下游设置**连接超时**与**读取超时**两套参数，并只对幂等请求做有限次重试。
- 网关排障先看状态码定位责任边界：502/504 查上游，499（Nginx）查客户端主动断开。

### 常见坑
- 把 `403` 当成「没登录」返回：客户端会反复跳登录页，实际是权限不足。
- 对 POST 盲目重试：可能造成重复下单、重复扣款。
- 用 `301` 做临时活动跳转：浏览器长期缓存，活动下线后用户仍被强跳。

### 面试怎么问
「接口超时了该不该重试？」先判断幂等性，再说超时时间、退避策略、幂等键与熔断，最后提「下游也可能已执行成功，只是响应丢了」，体现真实经验。

## 动手清单

### 练习 1：抓一次握手
用 `tcpdump -i any -nn port 80` 抓一次 curl 请求，找出 SYN / SYN+ACK / ACK 三个包，再观察连接复用时第二次请求是否还有握手。

### 练习 2：区分 502 与 504
本地起两个上游，一个返回非法响应、一个 sleep 不返回，通过 Nginx 反代分别观察状态码与日志。
**自测标准**：能解释三次握手为何不是两次、TIME_WAIT 属于谁，能说出 401/403、502/504 的区别并判断哪些请求可安全重试。
