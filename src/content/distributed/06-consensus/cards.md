# 06 共识、选主与脑裂

## Raft：先选出主，再复制日志

### 是什么
Raft 把共识问题拆成三个子问题：**选主（leader election）**、**日志复制（log replication）**、**安全性（safety）**。节点有 Follower / Candidate / Leader 三种状态；Follower 一段时间内没收到心跳就自增**任期（term）**转为 Candidate 拉票，拿到**过半数**选票即成为 Leader。所有写请求走 Leader，它把操作追加为日志条目并复制给 Follower，收到过半确认后才提交（commit）并应用状态机。

### 为什么
过半数（quorum）是关键：任意两个过半集合必然相交，因此新 Leader 一定包含已提交的日志，不会出现「两个主各自提交冲突数据」。任期号让旧 Leader 的心跳被新任期节点拒绝，从机制上阻止「僵尸主」继续写入。

### 怎么用
- 集群节点数取**奇数**（3、5、7）：3 节点容忍 1 故障，5 节点容忍 2 故障，偶数节点不增加容错反而多一台成本。
- ZooKeeper / etcd / Consul 的选主与配置分发、Nacos 的 Raft 模式、Kafka 的 Controller 选举都是这类机制。
- 应用层只需知道「写走 Leader、读可 Follower 但可能读到旧值」，强一致读要走 Leader 或 ReadIndex。

### 常见坑
- 以为「过半」是指超过全部节点的一半就行，却把集群扩成 4 节点：容错仍是 1，但写入要 3 票，可用性反而下降。
- 网络分区时少数派一侧仍在提供读：可能返回过期数据，需要按业务决定是保一致（拒绝服务）还是保可用。
- 把 Raft 当分布式锁用：它解决的是多副本状态一致，锁还需要租约与 fencing token。

### 面试怎么问
「Raft 怎么保证不会选出两个主？」答任期 + 过半投票 + 心跳，再补「任意两个多数派必相交」，最后提少数派分区应停止写入，链路就完整了。

## 脑裂与 fencing token

### 是什么
**脑裂（split-brain）**指网络分区后，两侧都认为对方挂了、各自选出或保留一个主，同时接受写入，恢复后数据冲突。即使有选主算法，如果旧主因 GC 停顿 / 网络抖动被误判死亡、但进程其实还活着并继续写，仍会出现「两个写者」——这就是**僵尸主**问题。

**fencing token** 是每次授予锁/主身份时单调递增的编号：持锁者带着 token 去写存储，存储层拒绝比已见过最大 token 更小的请求。这样即使旧主「以为自己还有锁」，它的写也会被下游挡掉。

### 为什么
仅靠「锁有过期时间」或「心跳超时判活」无法区分「进程真死了」和「只是慢了」。超时是**推测**，不是事实。fencing 把安全性下沉到资源层，不依赖时钟与超时判断的准确。

### 怎么用
- 选主系统配合**租约（lease）**：主身份有明确到期时间，到期前必须续约，续不上就主动降级为只读/拒绝写。
- 存储层校验 token（或版本号 / CAS），让「过期持有者」的写必然失败。
- 数据库兜底：唯一索引、乐观锁 version 字段，是最后一道不依赖任何中间件的防线。

### 常见坑
- 只靠 Redis 锁的过期时间防并发，不设 fencing：GC 停顿超过 TTL 后旧持有者恢复，会与新持有者同时写。
- 把心跳超时调得极短来「快速切主」，反而因偶发抖动频繁选主，形成**选主抖动**，写入持续中断。
- 分区恢复后不做数据对账，直接让两侧合并，冲突数据被悄悄覆盖。

### 面试怎么问
「分布式锁过期了业务还没执行完怎么办？」先答看门狗续期，再主动指出续期也挡不住进程暂停，需要 fencing token 或数据库版本号兜底——这一步是区分背过八股和真正想过的关键。

## 动手清单

### 练习 1：算一次 quorum
分别列出 3、4、5 节点集群的过半票数与可容忍故障数，解释为什么偶数节点不划算；再写出 5 节点发生 2:3 分区时，哪一侧能继续写。

### 练习 2：复现一次僵尸主
用两个进程模拟持锁写入：让进程 A 在拿到锁后 sleep 超过 TTL，进程 B 拿到锁也写同一行；观察无 fencing 时 A 的写覆盖了 B，再给写操作加单调递增 token 校验，确认旧 token 被拒绝。
**自测标准**：能解释「任意两个多数派必相交」，能说清为什么光有 TTL 和心跳还不够安全。
