# 05 数据分片与一致性哈希

## 为什么普通取模扩容会「全盘失效」

### 是什么
把数据分散到 N 个节点，最直觉的做法是 `hash(key) % N`。问题是 N 一变（加机器、宕机摘节点），几乎所有 key 的落点都会改变：原来在节点 3 的数据，扩容后可能落到节点 7。缓存场景下这意味着**同一时刻大批量缓存未命中**，请求直接压到数据库，就是常说的缓存雪崩的一种成因。

**一致性哈希**把节点和数据都映射到同一个 0～2^32 的哈希环上，数据沿环顺时针找到第一个节点。加一个节点时，只影响「新节点与它前一个节点之间」那一段数据，其余映射不变，需要迁移的数据量从接近 100% 降到约 1/N。

### 为什么
分布式系统的规模是变化的：大促扩容、故障摘除、灰度上线。如果每次拓扑变化都要全量重排数据，系统就没有弹性。一致性哈希把「加节点」的代价限制在局部，才有意义上水平扩展。

### 怎么用
- **虚拟节点**：每个物理节点在环上映射 100～200 个虚拟节点，避免数据集中在一小段弧上造成倾斜。
- 缓存分片（Redis 客户端分片、Memcached）用一致性哈希；数据库分库分表更常用「固定分片数 + 映射表」，避免直接按机器数取模。
- 扩容后先做数据迁移与双写校验，再切流量，最后逐步淘汰旧节点。

### 常见坑
- 以为一致性哈希就「不用迁移数据」：它只是**大幅减少**迁移量，受影响的那一段仍要搬迁。
- 不加虚拟节点：节点少时哈希环分布不均，少数节点承担大部分流量。
- 把 `hash(key) % N` 直接用在会扩容的缓存集群上，扩容当晚数据库被打挂。

### 面试怎么问
「Redis 加一台机器，为什么缓存大量失效？」先答取模导致映射全变，再说一致性哈希 + 虚拟节点把影响缩到一段弧，最后补一句「仍需迁移与预热，不是零成本」，层次就出来了。

## 分片键、跨片查询与热点 Key

### 是什么
**分片键（shard key）**决定一行数据落到哪个分片，例如订单表按 `user_id` 分片。选得好，同一用户的订单都落在一片，查询只需访问一个分片；选得不好，一次列表查询要扇出到所有分片再聚合。

分片之后，原本单库里理所当然的能力会受限：**跨片 JOIN**、**跨片事务**、**全局排序分页**、**全局唯一约束**都变贵或不再免费。因此分片键要跟着最主要的查询路径走。

**热点 Key** 是另一类问题：某个 key（秒杀商品、头部博主、全局配置）被远超单节点能力的频率访问，此时加分片也没用——因为它只落在一片上。

### 为什么
分片的本质是「用分布换容量」，代价是「失去全局视角」。热点 Key 则说明哈希只能分摊**均匀**的流量，分摊不了**倾斜**的流量。

### 怎么用
- 分片键优先选「高频查询条件 + 高基数」，比如按 `user_id` 而不是 `status`（只有几个值，必然倾斜）。
- 热点读：本地缓存 + 多副本 + 随机后缀打散（如 `sku:1001:0..9`），写多副本再合并。
- 大 Key（一个 list/hash 存了几十万元素）拆成多个小 key，避免单次操作阻塞单线程 Redis。
- 跨片排序改为「各片取 TopN 再归并」，或用离线宽表/搜索引擎承接。

### 常见坑
- 用低基数字段（性别、状态、月份）做分片键，数据全挤在一两片。
- 分片后仍写跨片 JOIN 与 `ORDER BY ... LIMIT 100000, 10` 深分页，延迟随分片数线性放大。
- 靠加锁保护热点库存，却不打散 key，所有请求仍排队在同一个 Redis 节点。

### 面试怎么问
「分库分表后有哪些坑？」按分片键选择 → 跨片 JOIN/事务/分页 → 全局 ID → 扩容迁移四层答，再主动提热点 Key 与数据倾斜，比只背「分片键」高一个档次。

## 动手清单

### 练习 1：亲眼看见取模的代价
写一段脚本，用 `hash % 3` 与 `hash % 4` 分别给 10000 个 key 分配节点，统计落点发生变化的比例；再实现带虚拟节点的一致性哈希，对比扩容时的迁移比例。

### 练习 2：设计一个分片键
给定「订单表：按用户查自己的订单、按商家查店铺订单、按订单号查单笔」，写出你会选的分片键、理由，以及另外两种查询如何兜底（冗余表 / 异构索引）。
**自测标准**：能说清一致性哈希为什么只需迁移 1/N 的数据，能列出分片后至少三种「不再免费」的能力。
