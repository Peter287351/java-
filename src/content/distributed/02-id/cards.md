## 为什么需要分布式 ID

### 是什么
分库分表后数据库自增主键只能保证单表唯一，跨库会撞号；同时业务常要求 ID 全局唯一、趋势递增（利于 B+Tree 索引）、有一定长度控制，部分场景还要求不暴露业务量。

### 怎么用
常见方案：UUID、数据库号段（一次取一段自增区间）、Redis INCR、雪花算法（Snowflake）。雪花把 64 位拆成时间戳、机器标识、序列号，本地生成不依赖中心节点。

### 常见坑
- UUID 无序，作为聚簇索引主键会造成页分裂与写入抖动。
- 自增 ID 会暴露每日订单量，对外接口可改用脱敏 ID。
- 号段模式重启会浪费一段 ID，但不会重复，属于可接受代价。

### 面试怎么问
「分库分表后主键怎么生成？」答雪花或号段，并说出趋势递增对索引的意义。

## 雪花算法与时钟回拨

### 是什么
Snowflake 典型结构：1 位符号 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号，同一毫秒内靠序列号区分，单机每毫秒可生成 4096 个 ID。

### 怎么用
每个实例必须配置全局唯一的 workerId（可用注册中心或数据库分配）；生成时判断时间戳是否小于上次，若回拨幅度小可等待，幅度大应拒绝并告警。

### 常见坑
- 机器 ID 重复 → 同一毫秒同一序列号 → ID 重复，是最常见事故。
- 时钟回拨会生成重复或小时间戳 ID，必须处理而不是忽略。
- 41 位时间戳有上限（约 69 年），选型时要算好起始纪元。

### 面试怎么问
「雪花算法时钟回拨怎么办？」答小幅等待、大幅拒绝并告警，同时保证 workerId 唯一。

## 动手清单
1. 用两个相同 workerId 的生成器并发生成 ID，复现重复；再改成不同 workerId 对比。
2. 推导 12 位序列号在单毫秒内的上限；自测标准：能算出单机每毫秒理论最大 ID 数。
