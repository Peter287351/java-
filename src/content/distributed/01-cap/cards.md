## CAP 与取舍

### 是什么
C 是一致性（所有节点同一时刻看到相同数据），A 是可用性（每个请求都能得到非错误响应），P 是分区容错（网络分区时系统仍能运行）。分布式网络里 P 无法回避，实际是在 C 与 A 之间取舍。

### 怎么用
选 CP：宁愿分区期间拒绝部分请求，也要保证数据一致（如 ZooKeeper、Consul、分布式锁）。选 AP：分区期间各节点继续服务，可能返回旧数据（如 Eureka、部分缓存场景）。

### 常见坑
- 「三选二」不是任意挑两个，而是分区发生时在 C 与 A 之间选。
- 单机数据库常说的 ACID 与 CAP 的 C 不是同一层面的概念。
- 把最终一致当成强一致用，会写出「写后立即读到旧值」的 bug。

### 面试怎么问
「注册中心为什么常选 AP？」答短暂拿到旧实例列表可用重试兜底，整体不可用代价更大。

## BASE 与一致性模型

### 是什么
BASE 是 Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致），是对 CAP 中 AP 方向的工程化表达。一致性从强到弱有：强一致、会话一致、单调读、最终一致。

### 怎么用
跨服务的数据同步多用消息队列 + 重试 + 对账达成最终一致；读自己的写这类场景可用「写后读主库」或会话粘滞来规避短暂不一致。

### 常见坑
- 最终一致必须有补偿与对账，否则不一致会永久留着。
- 用消息做同步时忘记幂等，重投会重复处理。
- Quorum（NWR）里 W + R > N 才能读到最新写入，配置错了还以为强一致。

### 面试怎么问
「怎么保证两个系统最终一致？」答本地消息表 / 事务消息 + 幂等消费 + 重试 + 定时对账。
