## 分布式事务的常见方案

### 是什么
一个本地事务只能覆盖一个数据库连接；跨服务、跨库的写操作需要额外协调。常见方案：2PC/XA（准备 + 提交，强一致但阻塞）、TCC（Try/Confirm/Cancel，业务侵入大）、Saga（一串本地事务 + 补偿）、本地消息表/事务消息（可靠事件 + 最终一致）、Seata AT（自动反向补偿）。

### 怎么用
强一致且参与者少可用 2PC；长流程、跨多个服务更适合 Saga 或消息驱动；大多数互联网业务选择最终一致 + 补偿 + 对账。

### 常见坑
- 2PC 在协调者故障时参与者会长时间持锁，吞吐差。
- TCC 的 Cancel 也要幂等，且要处理空回滚、悬挂等边界。
- 只发消息不落本地事务，会出现「本地回滚了但消息已发出」。

### 面试怎么问
「下单扣库存怎么保证一致？」答能接受最终一致就用事务消息 + 幂等消费 + 对账，强一致场景才考虑 2PC/TCC。

## 幂等设计

### 是什么
幂等是「同一操作执行一次与执行多次结果相同」。常用手段：数据库唯一键、状态机条件更新、幂等 token/去重表、请求指纹。

### 怎么用
写接口带业务唯一号（如订单号、支付流水号），数据库加唯一索引；更新用 `UPDATE ... SET status = 'PAID' WHERE id = ? AND status = 'UNPAID'`，靠影响行数判断是否已处理。

### 常见坑
- 只靠前端禁用按钮防重，网络重试或脚本调用照样重复提交。
- 幂等 key 选得太粗（如按用户），会误拦正常的不同请求。
- 去重表没有过期策略会无限膨胀，要按业务保留窗口归档。

### 面试怎么问
「重复支付怎么防？」答支付流水唯一键 + 状态机条件更新 + 幂等 token，并说明回调也要幂等。
