## 分布式锁的基本形态

### 是什么
多个实例要互斥地操作同一共享资源时，本地 synchronized / ReentrantLock 只能锁住本进程，需要外部协调者：Redis（SET key value NX EX）、ZooKeeper（临时顺序节点）、数据库唯一键。

### 怎么用
Redis 最简加锁：`SET lock:order:1 uuid NX EX 30`；解锁必须用「比对 value 再删除」的 Lua 脚本保证原子性。value 用唯一随机值，标识锁的持有者。

### 常见坑
- 先 GET 再 DEL 不是原子操作，可能删掉别人的锁；必须 Lua。
- 不设过期时间，持有者宕机后锁永远不释放。
- 过期时间比业务执行时间短，锁提前释放，第二个线程进来形成并发。

### 面试怎么问
「Redis 分布式锁怎么实现？」答 SET NX EX + 唯一 value + Lua 原子解锁 + 续期，并说出过期时间的两难。

## 续期、可重入与方案取舍

### 是什么
Redisson 的看门狗会在锁快到期但业务未结束时自动续期；可重入锁记录持有线程与重入次数。ZooKeeper 用临时节点 + 顺序节点 + 监听实现，客户端会话断开节点自动删除。

### 怎么用
锁粒度尽量小（按订单 ID 而不是整个订单表），持锁时间尽量短，锁内不要做远程调用。关键业务仍需在数据库层加唯一约束或状态机做最后兜底。

### 常见坑
- 看门狗依赖客户端存活，进程被 kill -9 后不再续期，锁最终仍会过期。
- Redis 主从切换时异步复制可能丢锁，RedLock 争议较大，强一致场景更倾向 ZooKeeper/etcd。
- 把分布式锁当「绝对正确」的唯一保障，忽略数据库兜底，一旦锁失效就会重复扣款。

### 面试怎么问
「锁过期了业务还没做完怎么办？」答续期（看门狗）+ 合理超时评估 + 数据库幂等兜底。

## 动手清单
1. 用 SET NX EX 实现加锁，分别演示「直接 DEL」与「Lua 比对 value 后 DEL」，说明两者差异。
2. 把锁过期时间设得比业务耗时短，复现两个线程同时进入临界区；自测标准：能说清续期的作用。
