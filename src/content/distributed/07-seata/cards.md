# 07 Seata 与分布式事务落地

## Seata 架构与 AT 模式

### 是什么
现有「分布式事务与幂等」一章讲的是**方案与思想**（2PC、TCC、Saga、本地消息表、幂等）。Seata 是把这些方案落成一个框架：一次全局事务由三个角色协作，**XID**（全局事务 ID）通过 RPC 上下文在各服务间透传。

| 角色 | 全称 | 位置 | 职责 |
|---|---|---|---|
| TC | Transaction Coordinator | 独立部署的 seata-server | 维护全局事务与分支事务状态，下发提交/回滚，管理**全局锁** |
| TM | Transaction Manager | 事务发起方应用内 | 由 `@GlobalTransactional` 标记，向 TC 开启全局事务，最终决定提交还是回滚 |
| RM | Resource Manager | 各分支应用内 | 代理 DataSource，向 TC 注册分支、上报状态、执行二阶段的提交或补偿 |

**AT 模式（Automatic Transaction）是 Seata 的默认模式，对业务侵入最低**：业务照常写本地 `@Transactional`，Seata 通过数据源代理把一次 SQL 拆成两阶段。

一阶段（RM 内部，全部在**同一个本地事务**里完成）：
1. 解析业务 SQL，拿到表、类型与条件；
2. 查**前镜像** before image（修改前的数据，通常带 `FOR UPDATE`）；
3. 执行业务 SQL；
4. 查**后镜像** after image（修改后的数据）；
5. 把前后镜像与 SQL 元信息写成一条 `undo_log` 记录，和业务数据一起提交；
6. 向 TC 注册分支并申请该行的**全局锁**（lock_key 一般是 表名:主键）。

注意：一阶段**本地事务就已经提交了**，本地行锁随即释放，这是 AT 比 XA 快的关键。

二阶段：
- **全局提交**：TC 异步通知各 RM，RM 只需异步删掉 `undo_log`，不做任何业务操作。
- **全局回滚**：RM 用 before image 生成反向 SQL 做补偿；补偿前必须用 after image 与当前数据库值比对，若不一致说明这行在全局事务期间被别的写操作改过（**脏写**），不能盲目回滚，要告警转人工。补偿本身也在本地事务里完成，并释放全局锁。

### 为什么
**全局锁**解决的是写隔离：一个全局事务还没最终决议前，不允许别的全局事务改同一行，否则回滚时补偿会把别人的写入覆盖掉。默认读隔离是「读已提交」，普通 SELECT 可能读到一阶段已提交、但全局事务尚未决议的中间数据；确实要读全局已提交状态，用 `SELECT ... FOR UPDATE` 配合 `@GlobalLock`，Seata 会检查全局锁并在冲突时抛异常让调用方重试。

### 怎么用
- 每个参与的业务库都要建 `undo_log` 表，且参与的数据源必须被 Seata 的 DataSourceProxy 代理，否则该分支不纳入全局事务。
- 全局事务范围**越小越好**：只包住必须同进同退的写库动作，RPC、MQ 发送、缓存操作、长耗时计算都放到事务外。
- TC 要集群化并用 DB / Redis 共享存储全局会话与锁；`file` 模式只适合本地开发。
- 业务异常必须**抛出**让 TM 感知，不能在 `@GlobalTransactional` 方法里 try-catch 吞掉后返回成功。

### 常见坑
- 以为 AT 是「两阶段都不提交」：一阶段已提交、数据库里能查到数据，别的连接普通 SELECT 也看得到。
- `undo_log` 没建或数据源没代理：全局回滚时该分支没有补偿依据，出现部分提交、部分回滚。
- AT 不适用于无主键表、复杂批量 SQL、存储过程、跨异构存储（Redis、MQ、ES），这些资源无法生成前后镜像。
- 回滚时发现 after image 与当前值不一致（脏写），却让程序自动覆盖回去，把别人的写丢了。

### 面试怎么问
「Seata AT 怎么做到无侵入回滚？」按「数据源代理 → 前后镜像 → undo_log 与业务同事务提交 → 一阶段就提交 → 二阶段异步删日志或按前镜像反向补偿 → 全局锁防脏写」这条链答，再补「读隔离默认读已提交，需要 @GlobalLock」。

## TCC、Saga、XA 与选型

### 是什么
| 模式 | 做法 | 一致性 | 代价 |
|---|---|---|---|
| AT | 框架自动记 undo_log 补偿 | 最终决议前的写隔离靠全局锁 | 侵入低，但只适用于关系型 DB 的简单 SQL |
| TCC | 业务手写 Try / Confirm / Cancel | 强一致的预留-确认模型 | 侵入高，每个操作写三个方法 + 事务控制表 |
| Saga | 长流程拆成多个正向步骤，每步配一个补偿步骤 | 最终一致 | 补偿不是回滚，流程编排复杂 |
| XA | 数据库原生两阶段提交 | 强一致 | 一阶段到二阶段全程持锁，吞吐差，依赖 DB 的 XA 支持 |

**TCC 三大坑必须用事务控制表（xid + branch_id + status）解决**：
- **空回滚**：Try 因网络超时根本没执行，TC 却下发了 Cancel；Cancel 查不到 Try 记录时必须直接返回成功，并记一条「已空回滚」，否则 TC 会一直重试。
- **悬挂**：Cancel 先执行完，迟到的 Try 才到达；Try 发现已有「已空回滚」记录必须直接拒绝，否则预留资源永远没人释放。
- **幂等**：Confirm / Cancel 都会被 TC 重试，必须靠状态字段做到重复调用只生效一次。

**Saga** 适合跨多个系统、耗时长的流程（下单 → 支付 → 发货 → 通知）。每个正向操作配一个业务补偿（发货了要发起退货、转账了要发起退款），补偿是**另一笔业务操作**，不等于数据库回滚，中间状态对外可见，所以只能保证最终一致。补偿同样必须幂等、可重试，并配状态机 / 事件编排与人工介入入口。

### 为什么
分布式事务没有银弹，选型的第一问不是「用哪个框架」，而是**「能不能不同步一致」**：能异步就别上强一致框架。互联网业务的主流答案是本地消息表 / 事务消息 + 消费端幂等 + 定时对账，吞吐高、故障域小。只有当多个数据库写操作必须同进同退、且调用方要同步拿到结果时，才值得引入 Seata。

### 怎么用
- 短流程、SQL 简单、跨 2～3 个同构 MySQL 库：AT 最省事。
- 涉及外部系统、需要精确预留资源（冻结余额、锁库存）：TCC，把预留与确认分开。
- 跨很多系统、耗时分钟级甚至更长：Saga 或消息驱动的最终一致。
- 强一致且参与者少、数据库支持 XA、能接受持锁：XA。
- 无论哪种，都要留**对账 + 人工补偿**这道最后防线，别指望框架 100% 兜住。

### 常见坑
- 把所有跨服务调用都套上 `@GlobalTransactional`，一个全局事务里塞十几个 RPC，超时与回滚概率飙升。
- 把 MQ 发送、Redis 写入放进 Seata 全局事务，以为能一起回滚——它们不产生 undo_log，回滚不了。
- TCC 的 Cancel 里直接扣回余额而不查状态，重试两次就多扣一次。
- Saga 里假设「补偿 = 撤销」，忽略钱已被消费、货已发出这类无法原样撤销的现实。

### 面试怎么问
「AT 和 TCC 怎么选？」先说 AT 侵入低但只覆盖简单 SQL 与关系库，TCC 侵入高但能精确控制预留、覆盖非 DB 资源；再补「能异步最终一致就别用这俩」，体现的是选型判断而不只是背概念。

## 生产落地与排障

### 是什么
TC 里存着全局事务会话、分支事务与全局锁（`global_table` / `branch_table` / `lock_table`），所以 **TC 本身必须高可用**：多节点 + 共享 DB / Redis；单点 TC 挂了，进行中的全局事务可能卡在未知状态。`undo_log` 会随着事务量增长，需要定期清理已决议的记录，并关注前后镜像过大（宽表、大字段）带来的写入放大。

### 为什么
分布式事务出问题时，现象往往不在框架本身，而在**热点数据与事务边界**：所有请求抢同一行库存，AT 的全局锁会把它们串行化，冲突的事务只能等待超时后回滚；全局事务包得越宽、持锁时间越长，冲突率越高，形成「并发越高成功率越低」的反常曲线。

### 怎么用
- 观测四组指标：全局事务开始/提交/回滚数、平均耗时与超时数、全局锁冲突次数与等待时长、`undo_log` 积压量与回滚失败数。
- 热点行治理：库存按 SKU 拆行 / 分桶预扣、队列串行化、缩短全局事务范围，或干脆改成 TCC 预留 / 消息最终一致。
- 超时与重试要有明确语义：调用下游超时**不等于**该分支一定失败，不能凭超时自行决定补偿；交给 TC 决议 + 分支状态查询。
- 回滚失败（脏写、undo_log 缺失、服务长时间不可用）要告警并转人工，配一张对账表按 XID / 业务单号核对各分支最终状态。
- 压测必须覆盖回滚路径：只测全成功链路，上线后第一次大面积回滚往往就是事故现场。

### 常见坑
- 业务代码 `catch` 住异常后返回成功，TM 以为一切正常直接提交全局事务，数据就此不一致。
- 把全局事务超时时间一味调大来「解决」锁冲突，只会让失败暴露得更晚、占用锁更久。
- `file` 模式的 TC 上了生产，重启后全局事务状态全丢。
- 只测提交不测回滚，等真出现脏写才发现 after image 校验与人工补偿流程没人演练过。

### 面试怎么问
「上了 Seata 之后压测反而更慢、失败更多，怎么排查？」按「先看全局锁冲突与回滚率 → 定位热点行与事务边界 → 缩短事务 / 拆热点 / 换模式 → 再加对账兜底」答，并主动说清 AT 与本地消息表的取舍。

## 动手清单

### 练习 1：画出 AT 的一阶段时间线
对着一个「写订单 + 扣库存」的例子，按顺序列出 before image、业务 SQL、after image、undo_log、注册分支、申请全局锁、本地提交这七步，并说明为什么一阶段提交后普通 SELECT 仍能查到未决议的数据。

### 练习 2：手写 TCC 的事务控制表
设计一张包含 xid、branch_id、status 的表，写出 Try / Confirm / Cancel 三段伪代码，说明它们分别如何处理空回滚、悬挂与幂等。

### 练习 3：做一次回滚演练
起一个最小 Seata 环境，人为制造「全局回滚时发现 after image 与当前值不一致」的脏写，记录框架行为并写出人工补偿方案；再用 try-catch 吞掉下游异常跑一遍，观察全局事务是被提交还是回滚。
**自测标准**：能说清 TC/TM/RM 各自职责、AT 一阶段为何能提前提交、全局锁解决什么问题、TCC 三大坑，以及「能异步就别上强一致框架」的选型理由。
