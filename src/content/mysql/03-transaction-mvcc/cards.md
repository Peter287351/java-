## 事务与 ACID：每个特性靠什么保证

### 是什么
事务是一组不可分割的 SQL 单元，满足 ACID：原子性（Atomicity，全做或全不做）、一致性（Consistency，数据从一个合法状态到另一个）、隔离性（Isolation，并发事务互不干扰）、持久性（Durability，提交即落盘）。

### 为什么
没有事务，转账"扣款成功、入账失败"这类部分失败就无法回滚；并发读写不加隔离，会读到中间状态。

### 怎么用
- 原子性：**undo log**（记录反向操作，回滚时执行）
- 持久性：**redo log**（WAL，先写日志再刷数据页，宕机后重放恢复）
- 隔离性：**MVCC + 锁**
- 一致性：由以上三者 + 应用层约束共同保证（一致性是目的，其余是手段）

### 常见坑
- 面试问"ACID 分别靠什么"最常答漏：一致性不是某个日志直接保证的。
- `autocommit=1` 时单条语句也是一个事务；多条语句业务要手动 `BEGIN ... COMMIT`。

### 面试怎么问
「一致性怎么保证？」——答"原子性+隔离性+持久性是手段，加上约束与应用层逻辑共同实现一致性"即可体现理解深度。

## MVCC：不加锁的读写并行

### 是什么
多版本并发控制：每行隐藏字段 `trx_id`（最后修改事务）与 `roll_pointer`（指向 undo log 版本链），读时用 **ReadView**（包含活跃事务列表 m_ids 等）沿版本链找对自己可见的版本。RC（读已提交）**每条** SELECT 生成新 ReadView；RR（可重复读）**事务内第一次** SELECT 生成并复用——这是两种隔离级别的本质区别。

### 为什么
读写不阻塞：写加锁，普通 SELECT 走快照读，既不脏读（RC 起）又保证 RR 内多次读一致。

### 怎么用
RR 下当前读（`SELECT ... FOR UPDATE`、`UPDATE/DELETE`）通过**临键锁**锁住范围防幻读；快照读靠 MVCC 防幻读。二者配合后 RR 实际可基本避免幻读，但"快照读之后紧跟当前读"仍能看到新行——因为当前读看的是最新数据。

### 常见坑
- 长事务让 undo 版本链无法 purge，越滚越长、查询变慢——务必避免大事务。
- MVCC 只作用于普通 SELECT；`FOR UPDATE` 是当前读，看最新已提交数据。

### 面试怎么问
「RC 和 RR 的实现差别一句话」——ReadView 的生成时机：一条一生成 vs 一次一生成。

## 动手清单

1. 两个会话分别开 RR 事务：A 快照读 → B 插入并提交 → A 再次快照读（看不到）→ A 执行 `UPDATE` 那条新行（当前读，能看到并改到）。自测标准：能解释为什么 UPDATE 后"突然看见了"。
2. 用 `SELECT * FROM information_schema.innodb_trx;` 找出运行超过 60 秒的事务。自测标准：能说出长事务两个危害（undo 膨胀、锁持有时间）。
