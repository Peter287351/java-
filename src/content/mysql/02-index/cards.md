# 02-index 知识卡

## B+ 树与索引的存储组织

### 是什么
InnoDB 的表按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存整行数据，非叶子节点只存主键和指针。二级索引（辅助索引）也是一棵 B+ 树，但叶子节点存的是"索引列 + 主键值"。

### 为什么 B+ 树适合磁盘
- 数据按 16KB 的页存取，读一页就是一次磁盘 IO。B+ 树非叶子节点不存数据，一页能容纳更多键，树更"矮胖"——千万级数据大约 3 层，定位一条记录约 3 次 IO。
- 相比红黑树等二叉结构，树高大幅降低；相比 B 树，叶子节点之间有双向链表相连，范围查询（BETWEEN、>、<、ORDER BY）顺着链表扫即可。
- 哈希索引只能等值匹配，不支持范围与排序，InnoDB 只在自适应哈希里局部使用。

### 常见坑
- 主键尽量自增或有序：新行顺序追加，页写满才开新页；用随机 UUID 做主键会造成频繁页分裂和碎片。
- 二级索引查非索引列要"回表"：拿着叶子里的主键回聚簇索引再查一次整行，所以 SELECT * 常常比只查索引列慢。

### 面试怎么问
「为什么用 B+ 树不用 B 树、红黑树、哈希？」——三个关键词：矮胖少 IO、叶子链表利范围查询、非叶子不存数据。

## 联合索引：最左前缀、覆盖索引与失效场景

### 是什么
联合索引 idx(a, b, c) 按"先按 a 排序，a 相同再按 b，b 相同再按 c"组织，因此：
- 必须从最左列开始连续匹配（最左前缀原则）：WHERE b=2 用不上；WHERE a=1 AND c=3 只用到 a。
- 遇到范围条件（>、<、BETWEEN、LIKE 'x%'）后，其后列的索引定位能力中断。

### 怎么用（覆盖索引）
查询的列全部包含在索引里（含主键），就无需回表，EXPLAIN 的 Extra 显示 Using index。例如 idx_name(name) 上执行 SELECT id, name FROM user WHERE name = 'tom'。高频 SQL 可以刻意把 SELECT 的列加进联合索引，用空间换时间。

### 常见坑（索引失效）
- 对索引列做函数或运算：YEAR(create_time)、id + 1 = 10。
- 隐式转换：phone 是 VARCHAR 却写 WHERE phone = 138xxx（相当于给列做 CAST）。
- 前导模糊 LIKE '%tom'；而 LIKE 'tom%' 是前缀匹配，可以走索引。
- OR 连接了无索引列（或跨列 OR 无 index merge 可用），整条 SQL 放弃索引。
- 设计口诀：等值条件列放前，排序列紧跟其后（ORDER BY 列接在等值列后可免 filesort）。

### 面试怎么问
「怎么判断索引失效？」——先跑 EXPLAIN 看 type 与 key，再从"列上是否做了函数/运算、类型是否匹配、最左前缀是否连续"三个方向排查。

## 动手清单

### 练习 1：亲手验证回表与覆盖索引
建一张 10 万行的 user 表并建 idx_name(name)，分别执行 EXPLAIN：
SELECT * FROM user WHERE name = 'u10000';
SELECT id, name FROM user WHERE name = 'u10000';
自测标准：能指出第二条的 Extra 出现 Using index（免回表），并解释为什么。

### 练习 2：验证失效场景
对同一个索引分别用 LIKE 'a%'、LIKE '%a'、UPPER(name) = 'A'、name = 123（varchar 列传数字）跑 EXPLAIN。
自测标准：能预测哪几种 type 变成 ALL，并说出各自的原因。
